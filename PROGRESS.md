- M3-11 classification order (spec discrepancy found 2026-11-23, spec not edited): the M3-7 classification checked the approval's status first, so a `failed` approval always returned `replay` — including one that failed because it ran out of retries. But the M3-11 test requires that exact case to return `exhausted` (after the third failure the approval is `failed` with `retry_count` 3, and a later execution must say the retries are used up). Neither DATABASE.md §5.3 step 2 nor ARCHITECTURE.md §5.5 pins the order between these two codes — they only list them — so the retry check now precedes the terminal-status check in `execute_approved_action` (migration `20261123171744_m3_execute_classification_order.sql`). A `failed` approval with retries left (for example one failed for tampering) still returns `replay`; only `retry_count >= 3` returns `exhausted`.
- M3-14 PGlite limitation (found 2026-11-23, spec not edited): PGlite accepts ALTER DEFAULT PRIVILEGES and then ignores it — `pg_default_acl` stays empty and a fresh function still gets PUBLIC execute. The audit proved it live: `anon` could call the internal helper `m3_settle`, and a probe function created after the ALTER still had `anon` execute. Fix: migration `20261123174117_m3_helper_revokes.sql` adds explicit REVOKE EXECUTE on the five `m3_*` helpers from PUBLIC, anon, authenticated, service_role (the SECURITY DEFINER callers run as owner, so they are unaffected). The ALTER DEFAULT PRIVILEGES statements stay in the migrations as the second layer for real Postgres. The M3-14 default-privileges test is therefore a static declaration check plus a tripwire asserting `pg_default_acl` is empty in PGlite; the behavioural live-database proof is deferred to the M3-27 security review. Also recorded in the test: the function catalog covers 13 API functions, not the 12 TASKS.md says (9 service-role M3 + 3 authenticated M3 + `save_document_extraction` from M5), plus 5 helpers with no API-role execute.
- M3-15 registry choices (spec does not pin them, recorded 2026-11-23): `get_tasks` takes an optional `status` filter whose values match the tasks table's status CHECK ('pending', 'completed') — the spec does not define get_tasks parameters, and a filter is the only sensible one for listing tasks. `save_memory` is risk high while `create_task` is risk medium: a saved memory is permanent and shapes every future conversation, unlike a task, which is one row the owner can complete or delete. Both still need approval; risk is display and gating metadata, not a bypass.
- M3-16 caps (spec says to cap number and size without pinning the numbers, recorded 2026-11-23): at most 20 memories and 4000 characters of fact text per request — 20 facts at roughly 200 characters each fits the budget, and the block says when more exist or when it was truncated instead of silently dropping them. A failed memory load does not fail the reply: the route logs it and answers without memories, because memories are background about the owner, not the answer itself.

ON CONFLICT (id) DO NOTHING`) and the bucket policies are plain SQL on `storage.objects`.
